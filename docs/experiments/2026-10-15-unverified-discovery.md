# Observing an agent-discovered finding without a prewritten checker

Approved follow-up to the runtime pilot, within the submission timebox. The previous pilot's finding came from an executable constitution. This run asks whether an agent investigating a real-looking bug report records useful new context, whether another agent receives it while it is still unverified, and what happens to their work. A failure to use the mechanism is a result, not permission to coach or rerun for a better story.

Three groups use the same small job service: vanilla Codex, Codex with an optional notes directory, and Superpose. Each has three concurrent gpt-6-luna / medium / default-tier sessions, no model fallback, with groups isolated and run sequentially. Vanilla receives only ordinary product tasks and repository documentation. No prescribed coordination, Git workflow, JSON reporting, finding, investigation protocol, or context-reset instruction. The worker's ordinary task is to investigate a customer-visible job-execution regression. Retry and CSV receive ordinary feature requests. Notes adds only the available directory. Superpose adds its usual claim/tool reference.

Every group starts with the same current runtime, service-28. An affordable pressure job is stopped; the legacy service-27 contract said budget_limit meant a spending refusal, while current evidence distinguishes temporary capacity from genuine budget stops. The bug report gives the symptom, not the cause or repair. Current source and read-only service diagnostics are equally accessible. The worker and retry tasks use that contract; CSV does not. Superpose represents the dated contract as an assumption linked to those two claims, and the product promise as a prose article. All groups can read the same dated contract and promise. No executable article or public test diagnoses the regression before the run. Existing module-load tests and tests the agents choose to write may run normally. The unchanged current-service snapshot is also committed for Cloudflare CI, where the coding container’s read-only runtime mount does not exist; both represent service-28, and no rollout occurs during this pilot.

Superpose's owner policy for this pilot publishes each newly filed finding to the same project's main line, preserving its unverified status. It never shares between experimental groups. Publication is logged separately from filing and receipt. This is an explicit owner policy exercised through the real publish API, not a claim that publication happens by default. The observer forwards only normal product notices, including uncertain advice; it supplies no diagnosis or private answer. There is no automatic verification of prose, no forced interruption, and no fresh-session intervention in this pilot. Final independent evaluation does not retroactively mark a finding verified during the run.

Before coding: qualify the portable real-Cloudflare recovery demo; acceptance and rejection controls for the fixture; a separate no-model Cloudflare rehearsal of unverified filing, local visibility, deliberate publication, actual scoped receipt, exclusion of unrelated work and absence of stale statuses. Qualify container mounts and denial of other-group API access before model turns. Those rehearsals are not experimental evidence of spontaneous discovery.

Per-role bounds: 50 actions, four minutes, $0.50 configured equivalent token usage. Three coding slots, one ordinary task per role, 15-minute live ceiling. The owner does not prompt agents to use findings if they omit them. Native product notices may reach active work, or an idle holder that still has its lease; this is counted and logged. No additional investigator or judge model. Report stalls, provider errors, budget interruptions and incomplete landings. Source hashes and prompts are frozen in the manifest.

Record discovery in the actual transcript, agent-authored findings or notes, uncertainty at publication, recipient presentation and response, unrelated work status, final integrated behavior, unintegrated native commits, time and usage. Distinguish a diagnosis spoken only in the final answer from a finding delivered to another worker. A shared-folder edit may inform the control implicitly; do not prescribe how it must happen. Final checks use isolated, read-only evaluation outside the coding containers. One small fixed-order run cannot establish a general advantage, and native branch/scoping/tool differences remain bundled.

Interpret the outcomes separately: no discovery; discovery without sharing; sharing without receipt; receipt without action; action without successful delivery; successful delivery. None is silently converted into another. Verification, contradiction-driven invalidation, fresh sessions and cross-project isolation policy were tested elsewhere; they are not newly demonstrated by this run unless directly observed.
