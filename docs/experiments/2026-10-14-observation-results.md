# First 6 luna observation run

All three groups produced a shop that passed all six independent checks: displayed versus paid price, real price increases, useful caching and expiry, correct orders, the catalog/home page, and the HTTP server. The main coordination experiment failed to exercise its intended finding-delivery-verification-recovery sequence; a product pass does not answer that question. Each group anticipated the interaction from explicit public promises and a page task requiring refresh on price changes. The [subsequent transcript review](2026-10-14-first-pilot-review.md) details the observations, protocol deviations and what remains unproven.

A single run does not support precise speed claims.

Every coding task used its own fresh `gpt-6-luna` session with medium effort. There were three concurrent slots per group, six tasks per group, and no inherited operator conversation or shared memory. Each task's tool execution used a separate Docker container without external networking. A gateway exposed only its own graph and explicitly granted Git repositories. The same Cloudflare Artifacts service hosted Git for every group. Code, messages, findings and fixes were not carried into later groups.

The matched Git agents proposed price and cache checks. Several referred to another task's files, so no independently qualified check from the proposer's scope was available. The server's submitted check matched the price promise in words, but passed the known broken integration too; it was declined. This is useful evidence that writing a plausible test is insufficient. The owner policy supplied requirements and qualification decisions without a repair algorithm. Replies were sometimes late; their latencies remain in the intervention journal. Requests copied through shared Git were not counted as fresh proposals from their readers.

Superpose recorded one advisory finding from pricing to purchase work and two proposed promises. The finding stayed unverified and was never explicitly published; it is absent from the purchase agent's saved context and notices. Filing did not demonstrate delivery. The owner adopted both proposals as prose matching already published price/order requirements. Neither supplied an executable check; an attempt to propose an in-scope order check hit inconsistent proposal-path requirements. No verified contradiction, rejected broken combination, or demonstrated repair was needed in this natural run. Active page/purchase agents received the pricing-adoption notice, but that repeated an existing requirement.

The first block, started at 18:39 UTC, was a launcher calibration failure. Its guard mispriced cumulative input/cached tokens as expensive output and interrupted work at roughly 170,000 tokens. Its outcomes and transcripts are preserved, including the interrupted ordinary Git group and unfinished Superpose changes. The corrected block started at 18:44 UTC with new contexts and repositories. This was an explicit infrastructure repeat, beyond the planned single block; it is not a concealed rerun selected for a favorable result.

Kevin asked whether concurrency caused those stops. The machine's BB limit was 20 threads, with no global limit and one active BB thread during the audit. These standalone Codex sessions use the launcher's separate three-agent limit. Interrupted transcripts contained no provider concurrency or rate-limit errors. Their totals reproduce the erroneous guard threshold exactly; all twelve Git task sessions then completed with the corrected guard and unchanged concurrency, including totals beyond the old cutoff. Current host load was about 3.7 on eight processors, with about 13 GB available memory. These observations identify the budget calculation as the recorded stop cause; resource contention could still affect timing.
